Attacked, measured, and reproducible from the repository

Synthetic data is sold as safe to share. This project attacked it to find out what it protects, and what it costs.

Hospital records, census answers and card transactions could power better research and better models, and privacy law keeps most of them locked away. The usual way out is synthetic data: a computer-generated table that keeps the patterns of the real one but is meant to contain none of the real people. Whether it really contains none of them is rarely checked. This project made synthetic copies of three public datasets of real people with seven different generators, some with a mathematical privacy guarantee and some without, and attacked every copy the way European regulators say anonymity should be tested. Then it asked what a data scientist would ask: does a model trained on the copy still work on real people?

The attacks stay inside each dataset: no outside data is ever joined to a record, and no record is ever named. Every rate is measured against a control group of real people the synthesiser never saw, so a table that is simply good at describing everyone is not counted as a leak. The basics, in plain words

Three ideas carry the rest of this page. If you work with synthetic data every day, skip ahead to the trade-off.

What a synthesiser is

A program that studies a real table, learns its patterns (how age relates to income, which diagnoses come with which procedures) and then writes a brand-new table of made-up rows with the same patterns. Nobody in the new table is supposed to be real. The danger is that it learns too much: if it memorises details of the real people it studied, the made-up table can give them away.

What a privacy guarantee is, and epsilon

Differential privacy is a mathematical promise: the output barely changes whether or not any one person was in the data, so it cannot reveal much about anyone. Epsilon sets how strong the promise is, and smaller is stronger. At epsilon 1, one person can change the odds of any result by at most a factor of about 2.7. Four of the seven synthesisers here make no such promise.

What "within 0.02 AUC" means

To judge usefulness, a model learns from the synthetic table and is tested on real people it has never seen. AUC scores how well it tells cases apart, from 0.5 (a coin toss) to 1.0 (perfect). Trained on the real census data, the model scores about 0.90 at spotting incomes above $50,000. Within 0.02 means the copy-trained model scores at least about 0.88.

The seven synthesisers in this study, one by one

Gaussian copula no guarantee

Classic statistics. It learns the shape of each column on its own, and how strongly each pair of columns moves together, then draws new rows that follow those shapes. Fast and simple, but it misses any pattern that is not a straight-line relationship.

CTGAN no guarantee

Two neural networks trained against each other. One invents rows; the other tries to tell invented rows from real ones. Each pushes the other to get better, until the invented rows are hard to tell apart.

TVAE no guarantee

A neural network that learns to squeeze each row into a short code and rebuild the row from it. New rows come from rebuilding codes it has never seen.

TabDDPM no guarantee

A diffusion model, the idea behind today's image generators, applied to tables. It learns to remove noise from a row a little at a time. To make a new row it starts from pure noise and cleans it up a thousand times.

MST privacy guarantee

Counts how often pairs of values occur together (say, age band and occupation) for the pairs that matter most, adds carefully measured random noise to those counts, then builds rows that agree with the noisy counts. It won the US National Institute of Standards and Technology's 2018 challenge for private synthetic data.

AIM privacy guarantee

A more adaptive MST. It picks which combinations of columns to count as it goes, spending its privacy budget wherever its current table is furthest from the real one.

PATE-CTGAN privacy guarantee

CTGAN with a guarantee. The network that judges real from invented is replaced by a panel of "teachers", each shown only its own slice of the real data. They vote, with noise added to the tally, so no single person can swing the result.

The four attacks, one by one

Singling out

Can the table be used to pick out one person? The attacker reads combinations of values off the synthetic rows, such as "a 67-year-old widowed pharmacist", and checks whether exactly one real person fits.

Linkability

Someone holds two separate halves of people's records. Can the synthetic table help them match the halves back together?

Inference

Someone already knows a few facts about a person. Can the table help them guess one more, such as an income bracket, a transaction amount or a diagnosis group?

Membership inference

The most direct question: can anyone tell whether a given person's record was used to make the table at all?

The first three are the tests named in the EU's guidance on anonymisation. Each one also runs on a control group of real people the synthesiser never saw, and only the extra success on the people it did see counts as risk.

Who needs the answer

Organisations hold data that could improve care, catch fraud and guide policy, and most of it cannot be shared, sometimes not even between teams. A synthetic copy is the shortcut everyone reaches for, and vendors sell it with a privacy score attached. That score is worked out by the same tool that made the data, when the test that counts is the one an attacker would run.

For a privacy officer

Whether a synthetic table passes the three tests of anonymity that regulators name, measured the way an attacker would and with a margin of error, instead of a vendor's similarity score.

For a data scientist

How much a model loses when it learns from the synthetic table instead of the real one, at each privacy level, and which synthesiser comes closest.

For whoever signs off

A rule, written down before any results came in, for how much privacy to buy and at what cost, and an independent release gate that checks the answer.

How it works

Make a copy, attack it, train on it

The rest of this page is the whole method and its results, in the order they happen. Each part starts in plain language, with a picture. Where there is more to say for someone who works on privacy or models for a living, it is folded away in a section you can open, so you can skip it if you only want the idea.

How it was tested

Three public datasets of real people: California census answers (ACS PUMS 2018), card transactions from a public fraud-detection competition (IEEE-CIS), and New York hospital discharges (SPARCS 2024). Each went through the same six steps.

  1. 1Split it three ways, once. One part trains the synthesisers, one is a control group of real people they never see, and one is kept back to test usefulness.
  2. 2Make synthetic copies seven ways. Four synthesisers without a privacy guarantee (Gaussian copula, CTGAN, TVAE, TabDDPM) and three with one (MST, AIM, PATE-CTGAN) at epsilon 0.5 to 8. Each copy is made three times, and every epsilon comes from the library's own privacy accounting.
  3. 3Attack every copy. Singling out, linkability and inference, built from the paper that turned the EU's three tests into measurements, plus a membership attack.
  4. 4Subtract what the table says about everyone. Each attack also runs on the control group. Only the extra success on the people the synthesiser actually saw counts as risk.
  5. 5Train on synthetic, test on real. A LightGBM model learns from each copy and is scored on real people it never saw, beside the same model trained on the real data.
  6. 6Apply a rule written in advance. Recommend the strongest privacy setting that keeps the model within 0.02 AUC of the real-data model on every task and run, with no attack detecting a risk. Then put the answer through a release gate.

Why the control group matters so much. A good synthetic table can predict a person's income from their job and age, because that is what it is for. Measured on its own, that looks like an attack working. Run the same attack on people the synthesiser never saw and it works just as often. Only the difference between the two is something the table learned about the real people in it.

As good as the real thing? The release gate says no

Project 03's release gate decides whether a new model is at least as good as the one it replaces, within a set margin. Here the new model learns from synthetic data and the old one from the real data. Since nothing met the rule, the gate was given the nearest candidates: for each dataset, the closest synthesiser overall (TabDDPM), the closest of the other no-privacy synthesisers (TVAE, or CTGAN on the hospital data), and the closest with a privacy guarantee. Each bar is the gap on the worst task, averaged over three runs, with the spread of the gate's 95 percent intervals.

The red line is the strict margin of 2 AUC points (0.02). The green line is the loss you would accept, set with the slider. The verdict on the right is the gate's own decision at that margin: it was run again at every whole point from 1 to 20, so each verdict is one the gate actually gave.

What leaked

A risk counts only when it clears a bar raised to allow for running five attacks on every configuration, with the three runs pooled. Here is what cleared it.

A leak is a finding about those settings on this data. It does not mean AIM is unsafe in general. And the tables where nothing was detected are not proven safe: these attacks, at this scale, could not break them.

Do the attacks catch what they should?

A clean result only means something if the same attacks catch a table that really does leak. So four methods people actually use as "synthetic" or "anonymised" data, each expected to leak, went through exactly the same process: the same splits, people, attacks and runs. Their settings and expected results were written into the plan before any of them ran. Each dot is one method's risk on one attack, with its 95 percent range. The grey tick is the highest risk any of the seven synthesisers reached on that attack.

The check most tools show got it backwards

Distance to closest record is the privacy check most synthetic-data tools show first. It asks whether the synthetic records sit closer to the real people the synthesiser trained on than to real people it never saw. A share above one half is read as a warning. Each dot is one configuration, averaged over its runs. The grey band is what real records the synthesiser never saw would score, so it shows where normal sits.

Why distance cannot see this kind of leak

The inference attack that works on AIM does not need any synthetic record to sit near a real person. It only needs the table to keep the link between the other attributes and income a little more faithfully for the people it trained on than for anyone else, and nearest-neighbour distance cannot see a link. It also errs the other way. A synthesiser that reproduces its training population well places its records slightly nearer that population than an independent sample would, and differential privacy allows that, because it limits what any one person changes, not how close the table sits to the population. The full write-up, with every number, is in docs/rejected.md.

Membership inference: at chance, and why that is not proof

The fourth attack asks the most direct question: was this person in the training data? It follows the Groundhog attack of Stadler and colleagues. Retrain the synthesiser dozens of times, with and without a target person, and teach a classifier to spot the difference from the tables alone. Because every one of those tables needs its own retraining, it runs on about 1,000 rows with six target people per dataset, the scale of the original paper. Each dot is one configuration's accuracy with its exact 95 percent interval; 0.5 is guessing.

Checked against the reference libraries

Every attack was written from its paper and then run beside the authors' own library on the same tables. Where the two disagreed, the cause was found and written down before any number went out.

What to take from it

These findings come from three datasets of 20,000 rows each, with these libraries and versions, and other data may give other numbers. The questions they raise apply to any synthetic data before it is shared.

Run the attacks on your own tables

The attacks are a stand-alone package. Give it the real records a synthesiser was trained on, the same number of real records it never saw, and the synthetic table. It prepares the columns using only the unseen records and returns every risk with its margin of error. 

from facsimile.attacks.evaluate import evaluate

result = evaluate(targets, control, synthetic, secret="income")
print(result.markdown())   # singling out, linkability, inference, with 95% intervals
result.detected            # the attacks whose risk interval excludes zero

Or from files: facsimile evaluate targets.csv control.csv synthetic.csv --secret income. What a result does and does not mean is in docs/attack-package.md.

What did not work

Distance to closest record as the privacy test

The check most tools show was expected to flag the tables that leak. It got the answer wrong both ways.

A TabDDPM leak on the census data

First reported through singling out. The reference library disagreed from run to run; averaged over five searches, the leak went in both versions and was withdrawn.

This project's first membership attack

Checked against TAPAS, its features were weaker, so every membership run was redone with the library's encoding: 9,720 synthesiser fits.

AIM at epsilon 4 and 8

One table ran for more than 28 hours and used up to 53 GB without finishing, so those cells were left out. At epsilon 2 AIM was already 0.10 to 0.17 AUC short of the bar.

The full write-up of the DCR test is in docs/rejected.md.

What this page does not show

  • No detected risk is not proof of safety. These attacks, at these sizes, could not tell the training records from the control group. A stronger attack, or more attempts, might.
  • The membership attack has little power at this scale. Even on a straight copy of the training data it does only a little better than chance, so a result at chance means it could not tell, and nothing more.
  • AIM at epsilon 4 and 8 was not run. At epsilon 4 one table ran for more than 28 hours and used up to 53 GB without finishing on a 32-core, 128 GB machine, and epsilon 8 grew faster still. At epsilon 2 AIM was already 0.10 to 0.17 AUC short of the bar, and no doubling of its budget gained more than 0.03, so the missing cells could not change the recommendation.
  • Three datasets, 20,000 rows each, one model. A larger table, other tasks or another downstream model could move the usefulness gaps. The method carries over; the exact numbers belong to these settings.
  • No defence is tested. The project measures tables. It does not post-process them to lower a risk.

How this was built

I designed this project and made the calls in it: what to attack, how to measure a leak, and what to do when a result looked wrong. When the first round of attacks found one risk in 48 configurations, I could not tell whether the tables were safe or the attacks were weak. So I put four methods that are expected to leak through the same attacks: a perturbed copy, SMOTE-NC, k-anonymity and an overfitted TVAE. The attacks caught every perturbed copy, SMOTE-NC and k-anonymity table. I added TabDDPM because the grid had no diffusion model, the kind most often found memorising its training data, and a second membership attacker because the first could barely spot a straight copy. When TabDDPM's one leak disagreed with the reference library from run to run, I wrote the rule for settling it into the plan before anything was rerun: every singling-out attack averages five searches, on every table, whichever way that cut, and the leak went.

I used an AI coding assistant (Claude Code) for implementation and drafting, which is now standard practice in software, data science and machine learning work. Every number on this page can be reproduced from the repository with one command, and the rule for recommending a privacy setting was fixed before any table was scored.

Some pieces come from my earlier projects: the statistics from Model Selection at a Tenth of the Cost, the release gate from AI Release Gate, and the card-transaction data terms from the Real-Time Fraud and Risk Decisioning Platform. Each attack I wrote from its paper and ran beside the authors' own library, Anonymeter or TAPAS, on the same tables.

Glossary
AUC
A score for how well a model tells two kinds of case apart, from 0.5 (a coin toss) to 1.0 (perfect). A gap of 0.02 is two points on that scale.
Bonferroni correction
Raising the bar for calling something detected when many tests are run at once, so that chance alone does not produce false alarms.
Confidence interval (95%)
The range the true value is likely to lie in, given how much data there was. A narrow range means a precise number.
Control group
Real people from the same population whom the synthesiser never saw. An attack's success on them is what the table reveals about anyone. Only the extra success on the people it did see counts as a leak.
Differential privacy
A mathematical promise that the output barely changes whether or not any one person was in the data.
Distance to closest record (DCR)
The share of synthetic records that sit closer to a training record than to an unseen one. Many tools show it as a privacy check. Here it got the answer wrong both ways.
Epsilon
How strong a differential privacy promise is. Smaller is stronger. At epsilon 1, one person can change the odds of any result by at most a factor of about 2.7.
Inference attack
Using the table to guess one more fact about a person, such as an income bracket, from facts already known.
Linkability
Using the table to match two separate halves of people's records back together.
Membership inference
Working out whether a given person's record was used to make the table at all.
Release gate
A statistical test that decides whether a new model is at least as good as the one it replaces, within a set margin, or declines to decide when there is too little data.
Singling out
Using the table to pick out one real person from a combination of their attributes.
Synthesiser
A program that learns the patterns in a real table and writes a new table of made-up rows with the same patterns.
Train on synthetic, test on real
The usefulness test: a model learns from the synthetic table and is scored on real people it has never seen, beside the same model trained on the real data.
